# Muse animation corpus and model-provenance plan

Status: researched proposal, 2026-10-30 (Europe/Dublin). This adds the corpus and provenance work needed by the [agent animation workflow](AGENT_ANIMATION_WORKFLOW_PLAN.md). It does not claim that the proposed generations, application changes or independent reviews have happened.

## Outcome and hackathon commitment

Build a broad, reproducible test suite whose actual animation artwork is generated by Meta Muse models. Prefer **Muse Spark 1.3 Contributor through Muse Code as the parent agent**, and **Muse Image as the pixel generator/editor**. Show that division of work in stored evidence, the web app, portable handoffs and training exports. A parent model's assertion that it made an image is insufficient evidence of which image model produced its pixels.

The [public hackathon page](https://cerebralvalley.ai/e/meta-ai-developer-hackathon) lists Muse Spark, Muse Wonder, Muse Image, SAM 3.1 and Muse Code. This is a product choice for this project; the authenticated submission rules and any exact model-use minimum remain separate in [SUBMISSION_REQUIREMENTS.md](SUBMISSION_REQUIREMENTS.md).

The suite should test tiny classical sprites, larger and richly coloured sprites, drawn and painted animation, material-based looks, rendered sprites, effects and complex scene motion. Quality means satisfying the declared animation request, preserving its chosen style, and detecting actual defects without condemning intentional artistic choices.

**Every generated benchmark sequence, failed generation and model-made repair must retain Muse generation evidence.** The verified-Muse cohort requires actual Muse generation evidence for every generated pixel ancestor; no non-Muse image fallback is allowed in that cohort. Framebound itself stays parent/provider agnostic and truthfully records other models. Existing procedural fixtures remain useful engineering controls in a separate cohort. Downloaded reference art, museum images, Blender renders and deterministic corruptions must never be relabelled as Muse-generated benchmark art.

## Research already gathered

The [reference gallery](research/muse-animation/index.html), [image manifest](research/muse-animation/reference-images.json), [source manifest](research/muse-animation/reference-sources.json), [style matrix](research/muse-animation/style-matrix.json) and [coverage table](research/muse-animation/COVERAGE.md) are checked in with this plan.

The seed library contains **273 unique downloaded image files and 142 source records, including 76 creator/asset-page leads and 66 museum artwork records**. One asset-page lead returned 404; source records preserve that result. Images retain source URLs, native dimensions, frame counts, byte hashes, creator/source information and publisher/institution licence declarations. The library includes 65 animated image files and seed assignments for 38 of the 48 proposed styles; ten styles still have acquisition gaps. Counts describe files, not independent subjects, animation frames, approved references or completed tests. A sprite-sheet preview and its original can be different files from the same reference family.

The library includes actual sprite sheets and animated previews alongside static appearance/material studies. Kenney, OpenGameArt submitters and RGS_Dev supply creator-published game-art references; the Cleveland Museum of Art supplies CC0-marked historical material and appearance references through its [Open Access API](https://www.clevelandart.org/open-access-api). Its [Open Access policy](https://www.clevelandart.org/open-access) distinguishes reusable public-domain images from other collection material. Source declarations and suitability still need pack-level curation. No seed pack is currently marked generation-ready.

Strong seed coverage exists for small pixel sprites, RPG/action/fighter sprites, drawn characters, isometric art, sketch, watercolour/paint/print appearance, and effects. Exact CGA/Spectrum, rubber-hose movement, paper/clay/fabric animation and several extension styles need more suitable references. The coverage table exposes those gaps rather than filling them with unrelated pictures. The linked source catalogue includes candidate images from sources not downloaded under the CC0-only acquisition rule.

## Model roles and verified setup

| Role | Preferred execution | What to record |
|---|---|---|
| Parent/orchestrator | Muse Spark 1.3 Contributor through Muse Code | Requested and observed model IDs, harness/version, effective Contributor setting, session/run IDs and tool-call lineage |
| Artwork generation and repair | Muse Image, exact available model version pinned per job | Actual model response, request/response IDs, supplied image bytes/order, prompt digest, output hashes and edit ancestry |
| Optional segmentation | SAM 3.1 through the existing bounded provider route | Model/version, source image hash, mask output and uncertainty; no artistic-approval claim |
| Optional model assessment | A separately recorded Muse execution | Assessor model/prompt/version, supplied evidence, uncertainty and relationship to the generator |
| Independent acceptance | Actual identified reviewers | Exact revision/evaluation, review rubric, defect labels and disagreements; no invented human identity |

[Meta's model page](https://dev.meta.ai/models/muse-spark) lists `muse-spark-1.3-contributor`. Local read-only checks found Muse Code **1.4.13 (1.4.13-R6996.1)**, an `exec` command supporting model selection, Contributor override, JSONL output and bounded steps, and a model profile resolving `muse-spark-1.3-contributor` at `max` effort. These checks prove local tooling/catalogue availability, not account access, image-call entitlement or a successful live request.

[Contributor mode documentation](https://dev.meta.ai/help/subscriptions/muse-code-contributor-mode) says Muse Code uses a setting, while API usage selects a Contributor model variant. Record the requested setting and its observed effective state separately; do not infer one from a friendly model label. Contributor processing includes supplied context, so curated public/cleared references and redacted project inputs must be selected before execution. Do not change account-wide settings as part of reference research.

[Muse Image documentation](https://dev.meta.ai/docs/image-generation) currently demonstrates `muse-image-1.0`, supports reference-conditioned generation and editing, and describes built-in grounding. Pin the actual available version at the live probe. Muse Code's text-model subscription is not evidence that image calls are included. Where supported, disable external grounding for benchmark generation and record that setting; otherwise label grounding visibility as unavailable and keep the case outside the strictly reference-controlled cohort. Do not claim complete reference closure when a provider does not expose its internal grounding inputs.

A future bounded parent launch can use the locally advertised interface:

```sh
muse model-profile show muse-spark-1.3-contributor --effort max
muse exec --model muse-spark-1.3-contributor --contributor-mode on \
  --reasoning-effort max --json --max-model-steps 24 \
  --workspace /absolute/path/to/framebound \
  --prompt-file /absolute/path/to/frozen-case-prompt.md
```

This is a proposed launch recipe, not a command run by this planning task. Provider calls must continue using the configured execution permissions, actual image-provider allowance and durable budgets. Preserve a redacted session/tool trace, not credentials or hidden chain-of-thought. Unknown upstream outcomes use the existing recovery path, never a blind retry.

## Style taxonomy

“8-bit”, “16-bit” and “32-bit” are historical aesthetic families, not universal limits on image width or colour count. Record **historical inspiration, native canvas, palette, alpha, contour treatment, view, material and animation technique as separate axes**. All working files may be RGBA PNGs, including a two-colour sprite. Historical hardware accuracy is an optional explicit contract with independently sourced specifications, not something inferred from an era tag.

The machine-readable matrix gives proposed sizes, palette treatment, defining traits, motion examples and actual seed-reference IDs for every style. Sizes below are proposed benchmark settings, not statements about hardware limits.

| IDs | Style families | Native-size direction / distinguishing requirements |
|---|---|---|
| P01–P05 | 1-bit monochrome; Game Boy inspired four-shade; NES inspired; CGA/Spectrum subvariants; PICO-8/fantasy console | Primarily 8–64 px; explicit palette snapshots, readable silhouettes and pixel clusters. Separate CGA and Spectrum contracts. |
| P06–P09 | 16-bit top-down RPG; 16-bit platform/action; large arcade/32-bit-era fighters; isometric pixel/tactics | 24–256 px; directional coverage, contact, anticipation, impacts, projection and overlap order. |
| P10–P12 | Pre-rendered 32-bit-era sprites; modern detailed pixel art; pixel actors in dimensional scenes | 64–1024 px by actor/scene role; richer colour, stable material/view and authored camera mapping. |
| D01–D06 | Flat vector; skeletal/cutout puppets; drawn cels; anime-inspired limited animation; rubber-hose; chibi | 128–1024 px; each style has different legitimate holds, deformation, pivots and contour behaviour. |
| D07–D12 | Pencil/ink sketch; comic/graphic novel; watercolour; gouache/oil; ink wash/woodcut; silhouette/shadow puppet | 128–1024 px; texture, line boil, translucency, ink marks and silhouette topology require different checks. |
| M01–M04 | Layered paper/collage; clay/plasticine; felt/knitted textile; voxel/block-built | Material-specific edges, seams, fibres, sculpted contact and intentional stepped timing. |
| R01–R04 | Low-poly rendered; cel/toon 3D; glossy toy forms; realistic painted/rendered sprites | 128–1024 px; geometry, lighting, highlights, anatomy and alpha require honest coverage reporting. |

| E01–E06 | Charcoal/chalk; pastel/crayon; stipple/engraving; risograph/screen print; emissive neon; dithered retro computer | Expansion set for texture, mark registration, compositing and palette stress tests. |
| E07–E12 | ASCII/character cells; embroidery/cross-stitch; mixed clay/paper; mechanical; glass/translucent; UI/icon/mascot motion | Expansion set for glyphs, grids, material boundaries, rigid pivots, transparency and endpoint readability. |

Reference research for historical context should also consult original publishers: [Nintendo's history](https://careers.nintendo.com/our-history/), [SEGA's Sonic Origins overview](https://sonic.sega.jp/SonicOrigins/about/), and [Square Enix's Octopath Traveler page](https://www.square-enix-games.com/en_US/games/octopath-traveler). These illustrate historical or dimensional-pixel presentation. Public screenshots are research links, not an automatic conditioning/training grant. Generate original characters and environments described by visual traits rather than reproducing franchise characters.

Technique sources include [Aseprite's animation documentation](https://www.aseprite.org/docs/animation), [sprite-sheet documentation](https://www.aseprite.org/docs/sprite-sheet/), [Krita's frame-animation workflow](https://docs.krita.org/en/user_manual/animation.html) and [Spine's example projects](https://us.esotericsoftware.com/spine-examples). These help distinguish drawings/holds from puppet deformation and presentation exports. They do not establish Framebound evaluator capability or permission to reuse example artwork.

## Reference packs: enough examples for every style

Before generating a scored case for any style, curate a versioned pack containing **at least 12 relevant images from at least three independent source/character families**. Prefer 18–24 images for broad or mixed-media styles. Three exports, crops or palette swaps of the same sheet still count as one family.

Each pack must cover:

- Four appearance references spanning at least three original subjects, with silhouette/line treatment and actual native-size information.
- Four motion/key-pose references spanning two actions; include contact, passing/transition and recovery poses, or equivalent effect stages. At least one example must expose real ordered timing. A still painting or arbitrary GIF preview is not proof of correct timing.
- Four palette/material/lighting references showing the relevant edges, shadows and texture at useful resolution. Reuse between roles must be declared; the pack still needs 12 distinct files and the source-family minimum.

For effects, substitute onset, peak, decay and loop/terminal behaviour for character poses. For paper, clay, textiles and 3D looks, add medium-specific close-ups and genuine motion examples; a photo of terracotta or embroidery is only a material reference. For hybrid styles, include both components and an example of their visual relationship.

Curation produces a short **style card**: defining traits, acceptable variation, forbidden accidental changes, native sizes, palette/alpha rules, timing convention, reference role assignments and why each image was selected. Use the references as evidence for these traits, not as interchangeable pictures behind a style name. Reject irrelevant search matches, broken files, duplicates and decorative logos/text. Registered crops retain their parent hash and exact crop operation; never overwrite a downloaded original.

A `ReferencePack` freezes its style-card digest and ordered asset IDs/hashes. Record source URL, creator, declaration/licence URL, acquisition time, rights/conditioning status, family, image/animation dimensions, animation timing source, transformations and review status. Distinguish `research_only`, `conditioning_ready` and `withheld`. The current downloaded library remains `not_curated`; no automatic pack approval follows from a source's CC0 declaration. Apply existing source/rights rules rather than creating a separate approval bureaucracy.

Do not send all references on every call. From the full curated pack, select a recorded 4–8-image conditioning subset that covers the current task and fits verified provider limits. Keep appearance, style/material, pose and scene instructions explicitly labelled and ordered. Hold out source/character families for evaluation; never leak hidden target poses or assessment answers into generation context.

Use one original Muse-generated character calibration sheet per style after the external pack is ready. Record it as a **Muse design proposal** with its own image-generation lineage. It stabilizes identity in later frames but does not become a human-approved motion reference. Any explicit known-good motion source needs its actual designation and authored-time map.

Reference acquisition is not finished until every promoted style meets the image, family and role gates. The full 48-style target needs at least **576 curated image assignments**, with actual unique-file and independent-family totals reported separately. Fill coverage gaps before promoting the corresponding style; do not disguise partial seed coverage as a completed reference pack.

## Motion and scene matrix

Cross style with the action and scene factors below using a balanced covering design rather than generating every Cartesian combination immediately.

| Factor | Required examples |
|---|---|
| Locomotion | Idle/breath/blink, walk, run, jump/land, climb, crawl, fly/flap, swim; quadruped and articulated-machine variants |
| Acting | Turnaround, look/reach, dialogue/mouth/eye hold, surprise, weight shift, squash/stretch, recovery |
| Interaction | Pick up/carry/place, push/pull, pass an object, touch/separate, strike/block, two subjects crossing/occluding |
| Effects/props | Fire, smoke, water, foliage, rotating coin/gear, dissolve, expansion/decay; explicit loop or terminal state |
| Camera/view | Fixed side, top-down, 3/4, isometric, 8-direction; pan, scale, parallax and a separately gated perspective-turn cohort |
| Timing | Two-frame economy, stepped holds, animation on twos/threes, smooth 12/24-fps output, nonuniform holds, loops and one-shot endpoints |
| Appearance difficulty | Tiny facial feature, distinctive costume/prop, repeated pattern, long hair/cloth, thin lines, soft alpha, reflective/translucent material |
| Scene difficulty | Partial/full occlusion, reappearance, similar-looking subjects, crossing tracks, changing light, busy background, contact and topology change |
| Optional source workflow | Native source enhancement, added detail, inserted in-betweens, unequal source/output counts, key preservation and authored-time correspondence |

Include both stationary cycles and genuine world displacement. A convincing treadmill walk and a correctly moving actor are different tasks. Do not fake new perspectives by horizontal flipping when the task requires asymmetric identity or actual turn geometry.

## Muse generation protocol

1. Freeze case intent, style card, identity, references, canvas, authored timing, permitted edits, requirements, evaluator applicability, split and budgets before execution. Choose which assumptions can actually be measured.
2. Bind a parent execution identity and actual Muse Code launch configuration. The parent calls Framebound CLI/MCP and the configured Muse Image route; the browser is not required to drive generation.
3. Generate original design anchors and a short native sequence. Compare joint sprite-sheet generation, anchor-conditioned frame generation and chained edits in a small pilot; retain the method as a factor instead of assuming independent frame calls preserve identity.
4. Save unmodified provider outputs and receipts before processing. Slice sheets only with recorded grid/rectangles and frame order. Record cropping, background removal, resizing, quantization, compositing and timing construction as derivations. Reuse Muse pixels; a script must not paint replacement art and call it Muse output. If native low-resolution sampling is required, retain both the source render and exact derivation and score the declared delivered representation.
5. Register immutable frames and a complete revision with targeted feedback and parent/generation identities. Evaluate, retrieve localized feedback and ask the Muse parent to produce a Muse Image correction within the frozen scope. Preserve failed results and the better earlier candidate.
6. Capture naturally occurring defects without selecting only successful runs. Generate separately requested negative variants through Muse Image for targeted challenges, and have reviewers verify what defects actually exist. A prompt requesting a missing hand is not a defect label. Deterministically corrupted Muse images belong to a separately labelled synthetic-control cohort with the Muse ancestor retained, not the naturally occurring Muse-failure cohort.
7. Stop at durable attempt, pixel, time and provider budgets. Save unknown outcomes, failed calls, refusals, ambiguous returns and no-progress events. Resume by identity; a new label cannot replenish the budget.

The image adapter must freeze the actual image-model request, references, order and selected mode. If an external parent bypasses Framebound's provider route, retain its actual redacted Muse tool trace and imported output hashes with `external_attested` provenance. Do not call that an observed Framebound dispatch. Opaque provider internals or unavailable seeds remain explicitly unknown. Reproducibility means recoverable inputs, outputs and derivations; it does not promise a nondeterministic service will regenerate identical pixels.

## First-class parent and generator provenance

The current v3 loop stores optional free-form `generation_metadata`; the old provider path also has durable request/origin evidence. Neither is sufficient to display a normalized, trustworthy parent-model history. Implement typed records additively, reusing actual provider evidence rather than duplicating it.

**Proposed `AgentExecutionIdentity`:** immutable ID, actor role, provider, requested model, observed/resolved model when exposed, harness name/version, observed model evidence source, Contributor requested/effective state and evidence, parent/session identifiers, start time and redacted trace artifact IDs/digests. `unknown` and `external_attested` are valid states. Do not create an SDK-observed claim from a model-supplied string.

**Proposed `GenerationEvent`:** actual execution identity, separate image-generator identity, input reference-pack/subset IDs and ordered hashes, prompt/request digest, image provider job/response IDs, original output hashes, edit parent, postprocessing derivations, actual origin, usage/cost when returned and the associated run/revision/frame IDs. A single generated sheet can parent many frames; a repair can have a different generator version. Preserve both facts.

**Proposed `ReferencePack` and `StyleCard`:** immutable versions with explicit roles, family relationships, curation status and conditioning eligibility. Reference assets remain `external_reference`; a Muse-generated calibration is a generated proposal with a generation event.

Record provenance at these boundaries:

- Task/run creation binds the initial parent execution. Each submission, handoff import, creative judgment and external failure report binds its actual actor execution. Parent changes/resumed sessions append events; they do not rewrite earlier attribution or reset run budgets.
- Each generation/edit binds the actual image model and provider evidence independently of the parent. Segmentation and assessment bind their own models. Multiple parents or specialists form an execution graph rather than one overwritten run-level string.
- A requested model, observed response model and resolved alias are separate fields. The configured preference for Muse is not proof that an old asset was generated by Muse. Parent or generator unknown means unknown.
- Human decisions retain authenticated reviewer provenance. Spark-generated labels remain `model_review`; technical pass remains technical evidence. Neither becomes independent human acceptance.
- Reference/source lineage and actual transmission subsets stay immutable through retries, derivatives, portable responses and exported closure. Do not expose API keys, auth headers, private paths or unrelated session content.

Example proposed submission evidence, abbreviated for readability:

```json
{
  "parent_execution_id": "parent-session-001",
  "generation_event_ids": ["muse-image-sheet-001"],
  "reference_pack_id": "P07-pack-v1",
  "parent": {
    "provider": "meta",
    "requested_model": "muse-spark-1.3-contributor",
    "observed_model": null,
    "harness": "muse-code",
    "harness_version": "1.4.13-R6996.1",
    "contributor_requested": true,
    "contributor_observed": null,
    "evidence_source": "external_attested"
  },
  "generator": {
    "requested_model": "muse-image-1.0",
    "observed_model": null,
    "response_id": null,
    "origin": "unverified_until_receipt_import"
  }
}
```

This illustrates unknown fields, not a completed live receipt. The literal IDs above are examples. A schema/parser must prevent an incomplete example from being counted as verified Muse generation.

### Framework and transport changes

Add typed services and additive tables for execution identities, generation events, style cards and reference packs. Back up existing projects, retain original payloads/digests, and provide a dry-run migration report. Link to existing immutable assets/provider jobs, v3 runs/revisions, saved feedback and exports. Preserve the reviewed-guide profile.

Expose matching create/get/bind operations through CLI, MCP and HTTP. Validate hashes, role/version bindings, actual observation source, replay and conflicts in the shared service. A caller may report external identity but cannot grant itself dispatch-observed provenance. Snapshot pins must freeze the execution/reference graph consistently with the selected trajectory.

Add capability negotiation for `parent-model-provenance-v1`, `reference-packs-v1` and `muse-generated-corpus-v1` (proposed names). Extend dataset/schema versions explicitly where required. Readers must reject unsupported semantics; an old run with no parent metadata stays unknown. Do not silently fill defaults into old hash-bound records or upgrade simulated evidence.

Extend portable handoffs with the selected public style card, appropriate reference subset and known parent/generator lineage. Returned corrections carry actual execution/generation evidence. A receiving project checks current task/feedback and edit authority as today. Provenance is evidence, not an execution token.

### Web app changes

Keep the current run-first film and inspector. Add compact, separate **Parent** and **Image model** fields to run/revision evidence, showing model ID/version, Muse Code harness and observed/attested/unknown status. On a historical revision these fields describe that revision, not the latest parent. A model change becomes a source-labelled timeline event.

The inspector should show the style card, palette/material assumptions and the actual reference subset sent for the selected generation. Reference previews open their source, role and provenance; they do not become the film's “Reference” lane. Only an explicitly designated known-good animation uses the source-comparison workflow.

Show segmentation/assessment models in expanded evidence. Keep human reviewer, parent satisfaction, technical status and output eligibility separate. The default view should not acquire a full provenance dashboard or another animated player.

## Evaluation and independently reviewed evidence

Do not run the declared-colour/landmark evaluator on painterly art and infer artistic accuracy from failed exact-RGBA matches. The existing structural, fixed-subject and tracked-scene profiles remain narrow. Choose declared measurable constraints where applicable; mark anatomy, perspective, complex material or motion judgments unmeasured until a supported method or actual assessment exists.

Annotate defects separately for identity/style drift, missing/extra features, temporal popping, undesired flicker, bad transition arcs, pose/contact errors, foot sliding, incorrect action/event, camera inconsistency, track swaps, loop seams, alpha fringes, palette/cluster violations and source-key/timing violations. Allow multiple real defects per clip, explicit uncertain labels and “not observable” states.

Maintain counterexamples: legitimate holds/repeated drawings, occlusion, motion blur/smears, squash/stretch, foreshortening, painterly line boil, controlled palette cycling, dissolving effects, deliberate area change and valid camera motion. Absence of an observable feature during declared occlusion must not be labelled disappearance.

Freeze development/calibration and held-out source/character/action families **before generation**. Group all related references, model-made identity anchors, failures, repairs, recolours, crops and near-duplicates. For model comparisons, reuse the frozen task/reference/timing contract and report actual model versions. Do not tune on held-out labels and then call the result held out.

Use a generation-independent review pass with blinded revision/model labels where practical. Prefer two actual reviewers plus adjudication for the final acceptance subset; retain reviewer identities, uncertainty, disagreements and incomplete labels. A separate Muse assessor can triage, but same-family model judgments are correlated evidence and never replace human labels by renaming the source. Reviewers may mark all attempts bad; no case needs an invented success.

Report precision/recall or false alarms/misses only where label coverage supports them; localize by native frame, authored time and ROI. Report per-style/action/model results, unmeasured/error rates, repair success and regressions, calls/cost/latency and completed/stopped counts with denominators. Use uncertainty intervals when sample sizes justify them. Keep development results, held-out results and human acceptance separate. The current benchmark's provenance fields should become typed links to the saved records while retaining compatibility with existing corpus manifests. Keep manifests below the existing 1,000-case limit, or introduce an explicit versioned shard index and aggregate reports; never silently truncate the larger planned corpus.

## Cohorts, budget and staged delivery

| Stage | Target, conditional on references and live probe | Exit evidence |
|---|---|---|
| A: provenance/reference foundation | Typed parent/generator records, curated first eight packs, one genuine Muse Image generation/edit/recovery probe | Actual redacted receipts, moved provenance closure, no fabricated live origin; adequate image entitlement and budget confirmed |
| B: hackathon pilot | Eight contrasting styles × four cases = 32 base clips; at most two repair/negative variants per base (96 revisions maximum) | Tiny pixel, 16-bit, large pixel, drawn, sketch/paint, material, rendered and VFX represented; actual per-style labels and failure history |
| C: broader corpus | 24 promoted styles × eight cases = 192 base clips; up to three revisions each = 576 revisions | Balanced actions/camera/occlusion, curated packs, independent review subset and held-out-family report |
| D: full core matrix | 36 promoted styles × 12 cases = 432 bases; up to 1,296 revisions | Every core style meets reference/role gates; measurable gaps and per-style false alarms/misses published |
| E: extension matrix | 48 promoted styles × 12 cases = 576 bases; up to 1,728 revisions | All extension packs curated and unsupported cases retained honestly |

These are corpus targets, not achieved counts, not an instruction to spend for the full matrix now, and not a promise that all stages fit before the hackathon. A variant can be a true model-made failure or repair; do not manufacture a pass to reach the table. Frames per clip depend on style/task, typically 8–24 in the pilot, with richer clips added only within decoded-pixel budgets.

Before each batch, freeze image-call/credit ceiling, maximum wall time, concurrency, decoded pixels, revision limits and a reserve for repairs. Measure one live pilot's real call/usage costs rather than estimating the image budget from Spark token prices. Account for multiple calls per sheet/edit and reference transmission. Stop on unknown charges/outcomes. Higher-resolution scenes may exceed default v3 pixel budgets; explicitly negotiate bounded task limits or shorter/chunked cases without changing the intended timing silently.

For the remaining hackathon window, prioritize A and B, then expand C only when the pilot is credible. Aim to freeze a demo/review subset before the existing 4 November 18:00 Dublin internal submission target. Reserve time for actual review, provenance packaging and portal requirements. A small measured Muse-generated suite is more useful than an unreviewed claim that hundreds of styles worked.

## Implementation PR sequence and acceptance checks

1. **Execution provenance:** typed additive storage/services and transport bindings; tests for replay, model alias unknowns, parent changes, conflicting imports, no credential leakage and older-record digest preservation.
2. **Reference packs and style cards:** manifest import/validation, family/role coverage, gallery/inspector integration and immutable conditioning subsets; tests for duplicates, missing files, swapped hashes, stale pack versions and source roles that do not imply approval.
3. **Muse corpus runner:** bounded Muse Code parent and existing image provider integration, receipt capture, sheet slicing/derivation, live resume and external-attested import; test simulated controls separately and prove one participant live generation/edit before advertising observed Muse origin.
4. **Web provenance and portable exports:** exact historical parent/image attribution, reference subset, timeline transitions, provenance filters and snapshot/reader capabilities; browser/API handoff, unknown-state and moved-export tests.
5. **Generated pilot and reviewed benchmark:** execute B, freeze real labels, retain all failures/repairs and report per-style coverage. Extend evaluator methods only with their own measured counterexamples; no retrospective blanket quality claim.
6. **Corpus expansion:** fill remaining reference/style gaps, execute C–E within explicit budgets and compare pinned Muse parent/image versions without leaking evaluation families.

Each code phase gets its own branch and remote PR, required checks and merge to main. Resolve conflicts while preserving other work. This research/plan PR introduces the plan, source catalogue and reference files; it does not implement the proposed runtime changes.

Completion requires a moved snapshot to explain **which parent model used which harness, which image model produced each asset, which reference bytes were supplied, which transformations followed, what checks ran, and who actually reviewed the result**. The framework and UI must show the same attribution. Only then can the Muse-generated, independently reviewed corpus close the remaining acceptance gap in the [implementation audit](AGENT_WORKFLOW_IMPLEMENTATION_AUDIT.md).
